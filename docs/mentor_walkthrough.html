InfraGuardianAn agentic infrastructure incident-response system — deterministic detection, LLM diagnosis, safety-gated action.

Picture three tireless junior engineers, each watching one dashboard — database health, host CPU/memory, GPU health — who never miss a threshold breach and never bother anyone unless something is actually wrong. When one of them spots a problem, they write a diagnosis. If two or three spot problems at once, a senior engineer reads every write-up and asks: is this one incident or three? What's really going on? Then — critically — that senior person follows a strict rulebook about what they're allowed to fix themselves versus what has to go to a human. That's InfraGuardian.

In one sentence Deterministic rules decide whether to call an LLM at all; specialist LLM agents diagnose anomalies per domain; a LangGraph orchestrator correlates their findings into one incident report; a deterministic safety gate decides to auto-fix, recommend, or escalate to a human — the LLM never decides whether it's allowed to act.

What it does, concretely

  • Ingests DB / CPU-memory / GPU metric samples (today: a deterministic simulator and two real collectors — more below) as validated Pydantic models.
  • Runs plain numeric threshold checks before any LLM call. A healthy domain never reaches a specialist — enforced structurally in the orchestrator's graph, not by convention.
  • For each anomalous domain, invokes a specialist LLM agent (in parallel) that returns a schema-valid root-cause finding — hypothesis, severity, evidence, and a verdict on whether it's safe to act on automatically.
  • If more than one domain fired, a synthesis LLM call correlates the findings into one unified incident report, explicitly labeling causal claims as hypotheses unless backed by measured evidence.
  • Confidence and severity are then recalibrated deterministically — the model's self-reported numbers never flow straight to the decision gate unchecked.
  • A pure-Python routing function decides: auto-remediate (from a fixed allowlist only), recommend to a human, or escalate — and every decision is logged with its rationale to a SQLite audit trail.

Why this is the interesting part (the actual portfolio pitch)

Bounded autonomy

The system is deliberately not "give an LLM shell access and hope." Every action is a predefined, allowlisted, reversible runbook. The LLM selects, it never writes, an action. That's the actual hard problem in production agentic systems — not "can the model answer," but "can I trust it with a blast radius."

Evaluation rigor

A 104-case evaluation harness with hand-derived expected outcomes (not generated by the code being tested) reports detection accuracy, root-cause accuracy, routing accuracy, schema validity, and — the number that matters most — a hard count of false auto-remediations.

Failure handling as a first-class citizen

What happens when the LLM call throws, times out, or returns malformed output? Every error path in this codebase fails closed — toward a human, never toward an unsupervised action.

Non-negotiable, every commit No arbitrary code/shell execution from model output. Critical-severity incidents never auto-remediate. Low-confidence findings fail closed. Malformed LLM output fails closed. Auto-remediation requires confidence ≥ 0.8 AND a safe allowlisted action AND severity below critical — all three, every time.

Portfolio framing: this is built to demonstrate production-oriented AI systems engineering judgment — bounded autonomy, evaluation rigor, failure handling — not shipped to real infrastructure. Execution of remediation is simulated by design (no real infra to act on in a portfolio project); the mechanism being demonstrated is the safety gate and audit trail.

Design properties worth calling out

  • Existing observability isn't replaced. InfraGuardian is a decision layer on top of metrics that are presumably already being collected somewhere — not a Datadog/Grafana competitor.
  • Three decision destinations, one audit sink. Whichever path a finding takes, the full reasoning trail lands in the incident store — nothing is "decided and forgotten."
  • No arbitrary action surface. The only arrow leaving InfraGuardian toward production infrastructure is through the allowlisted-runbook gate, in the auto-remediate path alone — recommend and escalate only ever reach a human.

orchestrator.pyThe LangGraph wiring: screen → (conditional fan-out to anomalous domains only) → specialists in parallel → synthesize → route_and_remediate. If zero specialists fired, synthesis is skipped entirely — an instant "all healthy" report, zero LLM calls.
tools/confidence.pycalibrate() caps the model's self-reported confidence against a deterministic ceiling — a hallucinated number cannot flow through to the gate unchecked.
tools/severity.pyseverity_floor() — the mirror of confidence calibration: certain threshold breaches (e.g. GPU ECC errors) carry a non-negotiable minimum severity the model cannot soften below.
tools/routing.pyroute() — plain Python, not an LLM call. Checks severity-critical and low-confidence first, unconditionally, before anything else.
tools/remediation.pyRUNBOOKS — the static allowlist. The LLM/routing layer selects an id from this dict; it can never construct executable text.
storage/incident_store.pySQLite: full incident reports + a UNIQUE(incident_id, runbook_id)-guarded action audit log (idempotent by construction).

The routing gate, in priority order (the safety-critical core)

  1. Severity == critical? → ESCALATE. Unconditional, checked first.
  2. Calibrated confidence < 0.5? → ESCALATE.
  3. Confidence ≥ 0.8, exactly one affected domain, that specialist said SAFE, and an allowlisted runbook exists for it? → AUTO_REMEDIATE with that runbook's id.
  4. Anything UNSAFE/UNKNOWN among contributing findings? → RECOMMEND (SAFE is a hard requirement for auto-remediation, not a tiebreaker).
  5. Two or more domains affected? → RECOMMEND (one runbook only ever targets one domain in this MVP, so cross-domain incidents never auto-remediate even at high confidence).
  6. Otherwise → RECOMMEND (medium confidence routes to human review).
Why confidence AND severity both get a deterministic floor/ceiling Real validation against Claude Haiku caught the model downgrading a GPU ECC fault from critical to high — which would have routed to RECOMMEND instead of ESCALATE for a hardware fault with a zero-tolerance threshold. severity_floor() exists specifically because confidence calibration alone doesn't catch a model softening the severity field.

Use casesWho this pattern is actually for.

Within this project's scope

On-call load reduction

Three domains monitored continuously; a human is only ever paged for what clears the escalation bar, and the narrow/safe/single-domain cases resolve themselves via an allowlisted runbook.

Cross-domain root-cause correlation

A DB connection-pool leak and a CPU spike showing up together might be one incident, not two — synthesis exists specifically to catch that instead of generating two disconnected tickets.

Pre-incident risk signal

Every specialist finding includes a predictive_risk field — "what happens next if this is left alone" — turning a threshold breach into a forward-looking signal, not just a snapshot.

Auditable automation

Every routing decision — including every non-action — is logged with its rationale, confidence, and the specific rule that drove it. Useful anywhere "why did the system do that" needs a real answer, not a log line.

The broader pattern (why this generalizes beyond infra)

Strip away the DB/CPU/GPU specifics and what's left is a reusable shape for any domain where an LLM should assist a high-stakes decision without being trusted with the blast radius alone: deterministic pre-filter → bounded specialist reasoning → deterministic recalibration → deterministic gate → allowlisted action. That shape shows up in:

  • Fraud/anomaly triage (flag deterministically, diagnose with an LLM, auto-block only within a narrow confidence+severity band).
  • Customer support auto-resolution (auto-close only low-risk, high-confidence, policy-safe cases; everything else goes to a human queue).
  • Any "agentic" system where the actual engineering question is "how do I bound what the model is allowed to do," not "can the model answer."
Why this is the right thing to show a mentor It's not "I called an LLM API." It's: here is a documented, testable, auditable boundary around model autonomy, with a number (zero false auto-remediations across 104 fixtures) to back the claim instead of a vibe.

What's honestly out of scope (said directly, not glossed over)

  • Execution of remediation is simulated — no real infrastructure is touched. The mechanism being proven is the safety gate and audit trail, not real remediation.
  • GPU domain is simulator-only; DB and CPU/mem both have real collectors (PostgresCollector, PsutilCollector) wired and demoed.
  • No auth/rate-limiting on the public API demo — by design, it only runs the offline fake model.
  • Not a Datadog/Grafana replacement, no production-grade PagerDuty/Slack integration, no model training — all explicitly out of scope per the PRD.
