What is InfraGuardian, really?The 60-second pitch, then the honest version.

Imagine three junior engineers who each watch one dashboard — database health, host CPU/memory, and GPU health — but never sleep, never miss a threshold breach, and never get called in unless something is actually wrong. When one of them sees a problem, they write up a diagnosis. If two or three of them see problems at the same time, a fourth, more senior person reads all their write-ups and decides: is this one incident or three? What's really going on? And then — critically — that senior person follows a strict rulebook about what they're allowed to do about it on their own, versus what has to go to a human. That's InfraGuardian.

In one sentence InfraGuardian is an agentic incident-response pipeline: deterministic rules decide whether to escalate to an LLM at all, specialist LLM "agents" diagnose anomalies per domain, a LangGraph orchestrator correlates their findings into one report, and a deterministic safety gate decides whether to auto-fix it, recommend a fix, or page a human — never letting the LLM itself decide whether it's allowed to act.

Why would someone care about this?

Three reasons, and they're the actual portfolio pitch (not just "I used LangGraph"):

1. Bounded autonomy

The system is deliberately not "give an LLM shell access and hope." Every action the system can take is a predefined, allowlisted, reversible runbook. The LLM picks from a menu; it never writes new commands. That's the actual hard problem in production AI systems — not "can the model answer," but "can I trust it with a blast radius."

2. Evaluation rigor

It's not a demo you eyeball once. There's a 104-case evaluation harness with hand-derived expected answers (not generated by the code being tested), reporting detection accuracy, root-cause accuracy, routing accuracy, and — the one that matters most — a hard count of false auto-remediations (currently zero).

3. Failure handling as a first-class citizen

What happens when the LLM call throws, times out, or returns garbage? Most demos don't even ask. This one answers it explicitly: everything fails closed — toward a human, never toward an unsupervised action.

Who is this for? (the honest framing)

This is a portfolio / FDE-style project — built to demonstrate production-oriented AI systems engineering judgment, not a product shipped to real infrastructure. That distinction matters a lot for how you talk about it in an interview, and it's confusing enough that it gets its own section later (jump to Section 8) — the short version: some things are deliberately excluded because the PRD says "not in scope" (real shell execution, real PagerDuty integration), and other things are missing because this isn't a 24/7 deployed service (no auth on the API, no CI pipeline). Both are "not done," but they say very different things about the design, and interviewers will probe which is which.

Jargon decoderEvery term you'll need before the architecture makes sense.

You said you didn't have the vocabulary yet — this is that vocabulary, in the order you'll actually encounter it, not alphabetical.

Agent / specialist agent

Not an autonomous robot. In this codebase it means one specific thing: a function that sends a structured prompt to an LLM and gets back a validated Pydantic object — nothing more. agents/db_agent.py::diagnose() is "the DB agent." It has no memory, no tools, no ability to call anything else. It's invoked once, per anomaly, and returns a typed finding.

LLM / specialist LLM calls

The actual language model (Claude, in the real-provider case) that reads the prompt and produces the finding. In this project it's swappable — see "model-agnostic" below.

Deterministic rule pre-screen

Plain if value > threshold checks — no LLM involved — that run first, against every incoming metric sample. If nothing breaches a threshold, the LLM is never called for that domain at all. This is the single most important cost/safety mechanic in the whole system: healthy infrastructure costs zero LLM tokens and has zero chance of a model hallucinating a problem that doesn't exist.

LangGraph / orchestrator / StateGraph

LangGraph is a library for wiring steps ("nodes") into a graph with explicit data flow between them — think of it as a typed state machine for multi-step LLM workflows. "The orchestrator" (orchestrator.py) is our graph: screen → specialists (in parallel) → synthesize → route_and_remediate. "StateGraph" is the specific LangGraph class that holds the shared state object threaded through every node.

Synthesis

The step where one more LLM call reads all the specialist findings together and asks: is there a relationship between these? E.g., "DB connection pool exhaustion" and "high CPU" showing up at the same time might be one incident (a connection leak eating CPU) or two unrelated ones. Synthesis produces the single unified incident report.

Correlation vs. causation (and "hypothesis" labeling)

Two things happening at the same time (correlation) is not proof that one caused the other (causation). The project's output contract requires every causal-sounding claim to be labeled a hypothesis unless there's directly measured evidence (like a traced query) — not just "these happened around the same time." This is enforced by a field: CrossDomainCorrelation.is_causal_hypothesis defaults to True and only a model with real evidence should ever set it False.

Confidence calibration

The LLM reports its own confidence (0–1) in its synthesis. We don't trust that number blindly — a model can be confidently wrong. tools/confidence.py caps the model's self-reported number against a deterministic ceiling computed from how many domains corroborate each other and whether the specialists judged their findings "safe." The gate downstream only ever sees this calibrated number, never the raw one.

Routing / routing decision

The final verdict on what happens to an incident: AUTO_REMEDIATE, RECOMMEND, or ESCALATE. Decided by a plain Python function (tools/routing.py::route()) — not an LLM call. This is deliberate: the most safety-critical decision in the system is the one place an LLM has zero say.

Allowlist / runbook

A "runbook" is one specific, pre-written, reversible fix (e.g. "recycle the DB connection pool"). The "allowlist" is the fixed set of runbooks that exist in code (tools/remediation.py::RUNBOOKS). The LLM can only ever select a runbook's ID string from this dict — it has no way to invent a new action or supply arbitrary text that gets executed. This is the entire mechanism behind "no arbitrary code execution from model output."

Idempotent / idempotency guard

"Running it twice has the same effect as running it once." If a retry or a duplicate request tries to execute the same fix for the same incident again, the system checks a database constraint first and refuses to double-execute. Enforced by a UNIQUE(incident_id, runbook_id) SQL constraint.

Fail closed / fail open

"Fail closed" means: when something goes wrong (a bad LLM response, a crashed tool call), the safe, restrictive outcome happens — escalate to a human. "Fail open" is the opposite and dangerous default: something breaks, and the system defaults to "allow it anyway." Every error path in this codebase is deliberately engineered to fail closed.

Model-agnostic

The code that talks to the LLM provider lives in exactly one file (tools/llm.py). Every other file calls one function, get_chat_model(), and has no idea whether that's Claude, Gemini, or a fake offline stand-in. Switching providers is an environment variable change, not a code change.

Fake model / FakeInfraGuardianModel

An offline, zero-cost stand-in for a real LLM — a lookup table that returns a canned, coherent (not random) finding based on which threshold rule was breached. It's the default when no API key is configured, so the entire pipeline, tests, and evaluation harness run instantly, offline, for free. It is explicitly not a claim about real model quality.

Pydantic / structured output / schema-valid

Pydantic is a Python library for defining a data shape (a "model") and automatically validating that incoming data matches it. "Structured output" means forcing the LLM to return JSON that fits one of these shapes exactly — with_structured_output(SomeModel) — instead of hoping you can parse free text. If the model's output doesn't fit, it raises an exception rather than silently returning something malformed.

Collector / collector abstraction

Whatever produces a metric sample. Today it's a "simulator" replaying a scripted scenario. Tomorrow (not built) it could be psutil reading real CPU stats or pynvml reading a real GPU. Both would implement the same .collect() interface, so nothing downstream (rules, agents, orchestrator) would need to change.

Step 1 — the sample arrives

Every metric reading is a validated Pydantic object: DBMetrics, CPUMemMetrics, or GPUMetrics, each extending a shared MetricSample base with a timestamp, domain, and source string. Today these come from SimulatorCollector replaying a hand-authored scenario; nothing downstream cares where they came from (that's the point of the collector abstraction).

Step 2 — the rule pre-screen (no LLM yet)

tools/thresholds.py::evaluate(sample) runs a handful of plain numeric comparisons specific to that domain — e.g. for DB: is p95 query latency > 200ms? Is the connection pool over 85% utilized? Is replication lag > 5s? Is the error rate > 2%? It returns a DetectionResult with is_anomalous: bool and the specific breached_rules, each with its observed value and threshold.

Why this exists before any LLM call This is the literal enforcement of "healthy domains must never reach a specialist." It's not a convention someone could forget — in orchestrator.py, the LangGraph conditional edge _route_anomalous_domains() only returns the names of domains that are anomalous. A healthy domain's specialist node is structurally never invoked for that run.

Step 3 — specialist agents run, in parallel, only for anomalous domains

Each specialist (agents/db_agent.py, cpu_mem_agent.py, gpu_agent.py) builds a domain-specific prompt describing the breached rules and calls get_chat_model().with_structured_output(SpecialistFinding). LangGraph fans these out as parallel branches — if DB and GPU are both anomalous, both specialists run concurrently, each writing only its own entry into a shared findings dict (merged via a custom reducer, more on that in Section 4).

Every specialist returns the exact same shape — a SpecialistFinding: root cause hypothesis, severity, predictive risk, evidence list, and crucially an automation_safety verdict (SAFE / UNSAFE / UNKNOWN) with a reason. That safety verdict is what the routing gate leans on later.

Step 4 — synthesis: one LLM call correlates everything

If one or more specialists fired, orchestrator.py::_synthesize() builds one more prompt containing all the findings and asks the model to produce a SynthesisOutput: a unified root cause, a list of cross-domain correlations (each explicitly labeled hypothesis-or-not), overall severity, a self-reported confidence, predictive risk, and priority-ordered recommended actions. If zero specialists fired (everything's healthy), synthesis is skipped entirely — no LLM call, an instant "all healthy" report.

Step 5 — confidence calibration (the model doesn't get the final word)

tools/confidence.py::calibrate() takes the model's self-reported confidence and caps it against a deterministic ceiling: 0.65 if only one domain is involved and that specialist wasn't confident it was SAFE; 0.95 if two-plus domains corroborate each other and all are SAFE; 0.8 otherwise. The routing gate downstream only ever sees this calibrated number.

Step 6 — the routing gate decides, deterministically

tools/routing.py::route() is plain Python, checked in a fixed priority order:

  1. Severity critical? → always ESCALATE. Full stop, no exceptions.
  2. Calibrated confidence < 0.5? → always ESCALATE.
  3. Confidence ≥ 0.8, exactly one domain affected, that specialist said SAFE, and a runbook exists for that domain? → AUTO_REMEDIATE, with the specific runbook ID.
  4. Anything UNSAFE/UNKNOWN among contributing findings? → RECOMMEND (SAFE across the board is a hard requirement for auto-remediation, not a tiebreaker).
  5. Two or more domains affected? → RECOMMEND, even at high confidence — explained in Section 8.
  6. Otherwise → RECOMMEND.

Step 7 — act, or don't

Only on AUTO_REMEDIATE does anything execute: the orchestrator checks a SQLite idempotency guard, then calls the selected runbook's execute() (a simulated, logged no-op in this MVP) and writes an audit row. RECOMMEND and ESCALATE just populate the report's fields — nothing runs.

Decisions worth being able to defend out loud

Why a fake, offline LLM by default? Judgment call

Early on, the LLM layer was required to be provider-agnostic (the user was still finalizing an API key and might switch providers for cost). Rather than block all development on that key, FakeInfraGuardianModel was built as the default: a deterministic lookup table keyed on breached-rule names, returning coherent canned findings. This means the entire pipeline, test suite (79 tests), and evaluation harness run instantly, for free, with no network access — which is also why CI never needs a secret to pass. It is explicitly documented as not simulating real reasoning quality.

Why is routing a plain function, not an LLM call?

Because it's the single most safety-critical decision in the system. An LLM call can hallucinate, drift, or be miscalibrated. A plain Python function with fixed if/elif branches, operating only on already-validated structured data, cannot — it's exhaustively testable (see Section 7's "safety invariant checklist" tests) and has no non-determinism to account for.

Why does confidence get capped instead of trusted?

Because a hallucinated or miscalibrated confidence number flowing straight into the auto-remediate gate is exactly the "fail open" failure mode the project's safety invariants exist to prevent. The calibration layer treats the model's number as a signal, not an authority — it can only be capped down from what a deterministic rule-based ceiling allows, never boosted up.

What actually broke during implementation? Real debugging

Good interview material — these are things that only surfaced once code actually ran:

  • LangGraph's merge requirement. The first cut of the orchestrator had every specialist node read-modify-write a shared findings dict directly. Running two specialists concurrently (the two-domain test case) raised InvalidUpdateError: Can receive only one value per step. Fix: give findings an explicit reducer (Annotated[dict, _merge_findings]) so each node only returns its own single-key update and LangGraph merges the branches itself.
  • StrEnum membership checks don't do what you'd expect. f.get("severity") in Severity raised a TypeError — StrEnum gives you string equality, not automatic in-membership against the enum class. Fixed by checking against {s.value for s in Severity} instead.
  • The fake model's canned confidence couldn't clear the auto-remediate bar. With the original canned value, the single most important demo (auto-remediation actually firing) couldn't be shown without a real API key. Fixed by raising the fake model's single-domain canned confidence from 0.75 to 0.9, keeping multi-domain confidence lower since those cases are routed to RECOMMEND regardless.
  • Fail-closed sentinel severity had to be CRITICAL, not HIGH. The first draft used HIGH severity for a failed specialist/synthesis call. During implementation it became clear that HIGH + UNKNOWN safety could still combine with a different domain's valid high-confidence finding and land outside the escalate path in some multi-domain cases. CRITICAL unconditionally trips the "critical never auto-remediates" gate (checked first, period) regardless of anything else — the stronger guarantee the safety requirement actually calls for.
  • Pydantic discriminated unions don't work with StrEnum fields. The FastAPI request schema tried to use domain: Domain as a discriminator, but Pydantic v2's discriminated-union feature requires a Literal type there. Fixed with a plain Union[DBMetrics, CPUMemMetrics, GPUMetrics] — Pydantic's "smart mode" matching works fine since each domain's model has non-overlapping required fields.

File-by-file tourWhat each script is for, and the one or two functions that matter in it.

Read these roughly in dependency order — each one builds on the ones before it.

tools/metrics.py

What it is: the typed contracts for every metric sample — Domain (a StrEnum: DB, CPU_MEM, GPU), MetricSample (shared base: timestamp, domain, source string), and three domain subclasses (DBMetrics, CPUMemMetrics, GPUMetrics) each with their own numeric fields and Pydantic range constraints (e.g. percentages bounded 0–100).

Why it matters: this is the ingestion boundary. Malformed data fails here, immediately, with a clear Pydantic error — not three layers deeper inside a specialist agent.

tools/collectors.py

What it is: MetricCollector, a structural Protocol (not a base class) requiring just one method, .collect(). SimulatorCollector is the only implementation — it replays a fixed list of samples one at a time, raising StopIteration when exhausted.

Why it matters: this is the literal swap point for going from simulated to real infrastructure. A real collector (psutil for CPU/mem, pynvml for GPU) just needs to expose the same .collect() method — nothing in the rule engine, agents, or orchestrator would need to change.

tools/scenarios.py

What it is: 12 hand-authored scenarios (4 per domain: 1 healthy + 3 degraded), each a literal fixed list of samples with an explicit numeric trajectory — no random number generation anywhere. E.g. _db_slow_query_degradation() hard-codes 8 timestamps with p95 latency climbing 50 → 70 → 110 → 180 → 260 → 340 → 410 → 460.

Why it matters: determinism here is a literal property — "run it twice, get the exact same thing" — not something that depends on correctly reproducing a random seed. That's a much easier thing to defend ("the trajectory is spelled out in code, there's nothing to reproduce") than a seeded RNG would be.

tools/thresholds.py

What it is: the deterministic rule pre-screen. Named threshold constants per domain (e.g. DB_LATENCY_P95_MS_MAX = 200.0, GPU_ECC_ERRORS_MAX = 0), one _evaluate_* function per domain returning a list of BreachedRules, and the public entry point evaluate(sample) -> DetectionResult.

Why it matters: this file has zero imports of any agent or LLM code — on purpose. It's the enforcement point for "healthy domains never reach an LLM," not just a convention someone could accidentally violate by importing the wrong thing.

agents/schemas.py

What it is: every shared Pydantic contract: Severity, AutomationSafety, RoutingDecision (all StrEnums), SpecialistFinding (one specialist's output), CrossDomainCorrelation, SynthesisOutput (what the synthesis LLM call produces), and IncidentReport (the final, canonical output every other layer — API, CLI, eval harness — is built against).

Why it matters: every LLM call in the project is bound to one of these models via with_structured_output(). "Schema-valid output" isn't a hope, it's enforced — a model that can't produce a valid instance raises an exception during .invoke().

tools/llm.py

What it is: the one and only module allowed to import a provider-specific LangChain package. get_chat_model() reads the INFRAGUARDIAN_MODEL env var and either calls LangChain's init_chat_model("provider:model") or, if unset, returns FakeInfraGuardianModel — an offline lookup table (_RULE_INFO) keyed on breached-rule names, with regex parsing (_build_specialist_finding, _build_synthesis_output) that reads the prompt text back out to decide what canned finding to return.

Why it matters: this is the actual mechanism behind "model-agnostic" — not a design claim, a one-file chokepoint everything else calls through.

agents/{db,cpu_mem,gpu}_agent.py

What it is: three nearly-identical files, each with one function, diagnose(sample, detection) -> SpecialistFinding. Each builds a domain-specific prompt describing the breached rules and observed values, then calls get_chat_model().with_structured_output(SpecialistFinding).

Why it matters: each agent has no opinion about when it runs — that's the orchestrator's job entirely. This separation is what makes "a healthy domain never invokes its specialist" enforceable from outside the agent itself.

tools/confidence.py

What it is: one function, calibrate(synthesis_confidence, findings, correlations) -> float. Returns min(synthesis_confidence, cap) where cap is 0.65 / 0.8 / 0.95 depending on domain count and automation-safety agreement (see Section 3, Step 5).

Why it matters: pure function, zero LLM dependency, trivially unit-testable — the kind of code you want sitting directly upstream of a safety gate.

tools/routing.py

What it is: one function, route(report, findings) -> RoutingResult, implementing the FR-12–14 gates as a fixed-priority if/elif chain (see Section 3, Step 6). Returns a decision, a human-readable reason string, and (if applicable) the runbook ID to execute.

Why it matters: this is the file where "critical never auto-remediates" and "low-confidence fails closed" are literal, checked-first lines of code, not aspirations.

tools/remediation.py

What it is: the allowlist. RUNBOOKS: dict[str, Runbook] has exactly three entries — db.recycle_connection_pool, cpu_mem.restart_worker_process, gpu.clear_memory_cache — each a frozen dataclass holding an execute() callable. get_runbook_for_domain() is a simple 1:1 lookup.

Why it matters: the LLM/routing layer can only ever select a runbook ID string from this fixed dict. There's no code path anywhere that takes LLM-generated text and executes it. Execution itself is simulated — logs what it would do, returns a canned success — which is stated plainly, not hidden (see Section 8).

storage/incident_store.py

What it is: a thin, direct sqlite3 wrapper, no ORM. Two tables: incidents (full report as JSON + indexed columns) and remediation_actions (the audit log, with a UNIQUE(incident_id, runbook_id) constraint). Functions: save_incident, get_incident, was_already_executed, record_remediation_action.

Why it matters: the UNIQUE constraint is the actual idempotency mechanism — not an in-memory check that could race or reset, a database-level guarantee.

orchestrator.py

What it is: the whole thing wired together as a LangGraph StateGraph. Key functions: _screen (runs the rule pre-screen for every domain present), _route_anomalous_domains (the conditional edge deciding which specialist nodes actually fire), _make_specialist_node (wraps a specialist call in a try/except that produces a fail-closed _sentinel_finding on any exception), _synthesize (builds the cross-domain prompt, calls the model, calibrates confidence, assembles the IncidentReport), and _route_and_remediate (calls route(), and on AUTO_REMEDIATE, checks idempotency and executes the runbook). The public entry point is run_incident(samples, persist=True).

Why it matters: this file is the answer to "how does it all fit together" — read _build_graph() at the bottom first to see the five-node graph shape, then read each node function in the order the graph calls them.

api/server.py & cli/main.py

What they are: two thin interfaces onto the same run_incident() call. FastAPI exposes POST /analyze (scenarios and/or raw samples in one body), GET /health, GET /metrics. The CLI exposes list, analyze, metrics subcommands via argparse.

Why it matters: neither has any pipeline logic of its own — they validate input (via Pydantic/argparse) and call the orchestrator. That's deliberate: interfaces shouldn't duplicate business logic.

tools/observability.py

What it is: _MetricsRecorder, a thread-safe (via threading.Lock), in-memory singleton (RECORDER) that the orchestrator writes to on every specialist/synthesis call and every completed incident. snapshot() computes failure rate, per-agent average latency, end-to-end p50/p95 latency, routing-decision distribution, and confidence distribution on demand.

Why it matters: the lock exists specifically because specialists run as concurrent LangGraph branches — without it, two domains finishing at the same instant could corrupt the recorder's internal lists.

evaluation/evaluator.py & evaluation/fixtures/*.py

What it is: run_evaluation() runs 87 hand-derived detection-accuracy cases and 17 hand-derived incident cases against the live rule engine and orchestrator (patched to use the fake model), computing the PRD §10 metrics table. Fixtures were derived by hand-tracing the scenario data through the threshold/calibration/routing logic — not generated by running the code being tested (see Section 7 for why that distinction matters).

Why it matters: this is the thing that turns "it works" into "here's the measured number, and here's proof the measurement isn't circular."

Safety deep-diveEvery PRD §9 invariant, and exactly where it lives in code.

These are the rules the whole project is built around. Each one maps to a specific, named piece of code — if an interviewer asks "how do you know X is actually true, not just stated," this is your answer for each.

InvariantWhere it's enforcedHow you'd prove it
No arbitrary code/shell execution from model output tools/remediation.py — RUNBOOKS dict The LLM only ever outputs a SpecialistFinding/SynthesisOutput Pydantic object — there's no field anywhere in those schemas for "command to run." Runbook execute callables are fixed Python functions defined in this file, period.
Every executable action maps to a predefined allowlist entry tools/routing.py::route() + tools/remediation.py::get_runbook_for_domain() Routing only ever returns a runbook_id that already exists as a key in RUNBOOKS — it's a dict lookup, not a constructed string.
Critical-severity incidents never auto-remediate tools/routing.py::route(), line 1 of the function test_routing.py has an explicit case for this; it's checked before confidence or safety are even looked at.
Low-confidence findings fail closed tools/routing.py::route(), checked second, unconditionally Confidence < 0.5 → ESCALATE, regardless of severity or safety.
Malformed/missing LLM output fails closed orchestrator.py::_sentinel_finding / _sentinel_synthesis_output Both sentinels force Severity.CRITICAL — which the routing gate above unconditionally escalates. A forced-failure test in test_orchestrator.py monkeypatches a specialist to raise and confirms the pipeline still completes and escalates, rather than crashing or defaulting to action.
Tool/API failures represented explicitly, never swallowed Same sentinel functions — the error text itself is embedded in root_cause_hypothesis/evidence, not discarded Read a sentinel-triggered report's JSON — the actual exception message is visible in the output.
Causal claims labeled hypothesis unless measured agents/schemas.py::CrossDomainCorrelation.is_causal_hypothesis, defaults True The synthesis prompt instructs the model to only set this False when evidence directly measures a causal link, not mere co-occurrence.
Remediations idempotent / guarded against duplicate execution storage/incident_store.py — UNIQUE(incident_id, runbook_id) + was_already_executed() checked before every execute() call test_incident_store.py round-trips this directly: false before execution, true after.
Auto-remediation gate: confidence ≥ 0.8 AND safe allowlist action AND severity < critical tools/routing.py::route(), the single AUTO_REMEDIATE branch All three conditions are in one if statement — there's no code path that can trigger auto-remediation satisfying only two of the three.
The one demo that proves it, end to end Run the gpu_ecc_errors scenario. The fake model reports confidence 0.65 for that finding — comfortably inside what would be an auto-remediate range if severity weren't considered. But ECC errors are hard-mapped to Severity.CRITICAL (tools/llm.py's _RULE_INFO), and the routing gate checks severity first, unconditionally. Result: routing_decision: "escalate", no runbook executed, no auto-remediation — even though confidence alone wouldn't have blocked it. This is the single most important thing to show working in an interview, because it's the one case where two signals disagree and the safety gate still wins.

How we proved it worksThe evaluation harness, the numbers, and why they're not circular.

The core idea the harness has to get right

It's trivially easy to build an "evaluation" that always reports 100% — just generate expected answers by running the code you're testing and recording whatever it returned. That would catch nothing. The fixtures here are built the opposite way: evaluation/fixtures/detection_cases.py's 87 cases and evaluation/fixtures/incident_cases.py's 17 cases were derived by hand — tracing each scenario's literal numeric trajectory (from tools/scenarios.py) against the threshold constants (tools/thresholds.py) and the fake model's canned rule table, calibration formula, and routing gates, entirely independently of running the pipeline. If a real bug landed in the threshold constants or the routing logic, this harness would actually catch it.

The latency numbers in particular mean almost nothing on their own (no network round-trip); what they prove is that the orchestration/routing/calibration machinery itself adds negligible overhead. Real-provider latency and cost are an explicitly deferred follow-up (see Section 8) — not because they're unimportant, but because the model-agnostic design means turning that on is a config change, not new code.

What the test suite covers (79 tests)

Beyond the eval harness: metric contracts, the rule engine (every scenario's first and last sample classified correctly — "scenarios start healthy and degrade" as an executable invariant), the fake model, specialist agents, LangGraph fan-out/fan-in and synthesis, confidence calibration, a dedicated table-driven routing test file that is effectively a safety-invariant checklist (critical-never-auto-remediates and low-confidence-always-escalates are explicit named test cases, not incidental coverage), remediation runbooks, incident-store idempotency, the orchestrator's fail-closed behavior on a raising specialist, the API, and the evaluation harness itself — all offline, no network or API key required, which is also what makes this safe to run in CI with zero secrets.

There are two completely different kinds of "not done" in this project, and conflating them makes you sound like you don't understand your own design. Here's the test: ask "did the PRD say we're explicitly not doing this, or did we just not get to it because this isn't a 24/7 deployed service?" Those are different answers to "why isn't X here," and interviewers can tell the difference.

Deliberately out of scope

Things the PRD says, up front, "we are not building this, on purpose" — a design decision, not a shortfall. If asked "why doesn't it do X," the right answer is "because doing X would violate the thing this project is actually trying to demonstrate (bounded autonomy), not because we ran out of time."

  • No arbitrary shell/code execution by the model — ever, by design, not "not yet."
  • No fully-autonomous remediation of critical incidents — the safety gate structurally prevents this.
  • No real PagerDuty/Slack integration — stated as out of MVP scope from day one.
  • No model training or fine-tuning — this project is about orchestration and safety engineering around an LLM, not about the LLM itself.
  • Not a Datadog/Grafana replacement — it's an incident-response decision layer, not a metrics platform.

Gap because it's a portfolio build

Things that would be required before this could run as a real, trusted, 24/7 service, but weren't built because this is a demonstration of engineering judgment, not a product with production SLAs and real users. If asked about these, the right answer is "yes, that's a known gap, here's exactly what I'd need to add and why I didn't need it to prove the point this project is making."

  • No auth or rate-limiting on the FastAPI endpoints.
  • SQLite is single-writer — fine for one process, not for horizontally-scaled replicas (Postgres is the PRD's own stated post-MVP path).
  • No CI pipeline wired up (even though the test suite is fully offline and CI-ready).
  • No secrets management (API keys are plain env vars).
  • No structured logging / log aggregation across replicas.
  • Observability is in-memory per-process — restarting the process loses it, and it wouldn't aggregate across multiple replicas.
  • No retry/backoff on transient LLM API failures — a transient failure fails closed to escalate, which is safe, but a production service would want a retry first.
  • Thresholds and the confidence-calibration formula are judgment calls defensible for this project's scenarios, not baselined against real historical incident data.
The one-line version to say in an interview "The non-goals are architectural boundaries I designed around — building past them would undermine the point of the project. The portfolio gaps are operational hardening I'd add before trusting this with real traffic — none of them require re-architecting anything, because the collector abstraction and model-agnostic LLM layer were built specifically so that hardening is additive, not a rewrite."

Why this split matters for how the code is organized

Notice that almost every "portfolio gap" above is infrastructure around the core pipeline (auth, logging, retries, a real database), while every "deliberately out of scope" item is a property of the pipeline's own design (what the LLM is and isn't allowed to touch). That's not a coincidence — it's exactly the collector-abstraction and allowlist patterns doing their job: the core safety-critical logic doesn't need to change to add the missing operational layer later.

Interview Q&A rehearsalClick a question, think of your answer, then check it.

These are the questions this project is actually built to answer well. Try to answer out loud before revealing — that's the whole point of rehearsing.

Q: Walk me through what happens when a metric comes in.
It's validated against a Pydantic contract (DBMetrics/CPUMemMetrics/GPUMetrics), then run through a deterministic threshold check with no LLM involved. Only if a threshold is breached does it reach a specialist LLM agent — healthy metrics never cost a token or risk a hallucinated problem.
Q: How do you know the LLM can't do something dangerous?
The LLM's only outputs are schema-validated Pydantic objects (findings, a synthesis) — there's no field for "command to run." The actual decision to act, and which action, is made by a separate deterministic function that selects from a fixed allowlist dict defined in code. The LLM can at most select an ID from that list; it has no path to construct new executable behavior.
Q: What happens if the LLM call fails or times out?
The orchestrator wraps every LLM call in a try/except. On failure, it constructs a "sentinel" finding/synthesis object with severity forced to CRITICAL and the actual exception message embedded in the evidence — so the failure is visible, not swallowed — and CRITICAL severity unconditionally routes to ESCALATE. The system never defaults to inaction being silently misreported as "healthy," and never defaults to auto-remediating on uncertain data.
Q: Why is routing not itself an LLM call?
Because it's the single highest-stakes decision in the system, and LLM calls introduce exactly the kind of nondeterminism and potential-for-hallucination you don't want at that point. Routing runs after structured parsing has already either succeeded or been replaced by a fail-closed sentinel — there's nothing left for malformed output to corrupt at that stage, which is exactly why it's safe to make it a plain, exhaustively-testable function.
Q: How did you validate accuracy, not just "it runs"?
A 104-case evaluation harness where expected results were hand-derived independently from the code under test — by tracing scenario data through the threshold constants and routing logic by hand, not by running the pipeline and recording its own output. That's the difference between a real regression test and a tautology.
Q: What's the biggest limitation of the current MVP?
Cross-domain incidents always route to RECOMMEND at minimum, even at high confidence with every contributing finding marked SAFE — because a single runbook only ever targets one domain, and auto-executing one domain's fix while leaving a corroborated second domain unaddressed is a scope mismatch this MVP doesn't attempt to solve. That's a deliberate, documented MVP boundary, not an oversight.
Q: What would you need before this could run against real infrastructure?
Swap SimulatorCollector for real collectors (psutil/pynvml/DB status queries) implementing the same .collect() Protocol — no change needed to the rule engine, agents, or orchestrator, because that boundary was built to be swappable from the start. Separately, operational hardening: auth on the API, Postgres instead of SQLite for multi-replica writes, a real retry/backoff policy on LLM calls, and thresholds re-baselined from real historical incident data instead of judgment calls.
Q: Why build a fake offline model instead of just requiring an API key?
So the entire pipeline, 79-test suite, and evaluation harness run instantly, for free, with zero network dependency — which also means CI never needs a secret to pass. It's explicitly documented as a lookup table, not a claim about real LLM reasoning quality; real reasoning quality is a separate, not-yet-measured question deferred until a provider key is configured, which the model-agnostic design makes a config change, not a rebuild.
Q: What's one thing that broke during development that taught you something non-obvious?
LangGraph requires an explicit merge/reducer function for any state key more than one parallel node writes to. The first version had specialist nodes read-modify-write a shared dict directly, which raised InvalidUpdateError the moment two specialists ran concurrently. The fix — give the state key an Annotated reducer and have each node return only its own single-key update — is the concrete mechanic behind "parallel execution isn't free, it needs explicit state-merge semantics."
